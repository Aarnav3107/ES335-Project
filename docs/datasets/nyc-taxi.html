Case study 01 / NYC Yellow Taxi, January 2016 / Regression

How messy data hid a perfectly good feature

We wanted to predict how long a New York taxi trip will take, using only what we know when the passenger gets in. The obvious feature, the distance between pickup and dropoff, did almost nothing at first, and it took a lot of digging through the data before we understood why. That digging turned out to be the real lesson of this case study.

CHAPTER 01

What we are trying to predict

The question itself is simple: when a passenger gets into a taxi, can we estimate how many minutes the trip will take? At that moment we know where they are, where they want to go, how many passengers there are and what time it is. The target is the difference between the dropoff and pickup timestamps, measured in minutes.

There is one rule you have to be really strict about here. Some columns are only known once the trip is over, like the dropoff time, the distance the meter recorded and the average speed. If any of those sneak into the model it will look brilliant on paper and be useless in practice, because it is basically reading the answer. We still used those columns to hunt down broken records, but none of them goes into the model.

CHAPTER 02

Why the obvious feature didn’t work at first

Our first attempt at using distance was a real disappointment. We computed the straight-line distance between pickup and dropoff, gave it to Linear Regression, and the RMSE barely moved: 52.7959 minutes without it and 52.7962 with it. A trip’s length has to matter for how long it takes, so that result made no sense, and we went back to look at the data itself.

When we looked closely, the data turned out to be full of problems. More than 150,000 trips had a pickup at coordinates of exactly zero, some locations were nowhere near New York, more than eleven thousand trips had a duration of zero or less, and one trip supposedly lasted 83 days. Before trying any stronger model, we needed a clear definition of which trips we were actually going to model.

The cleaning rules we settled on

Think of these as limits on what we chose to model rather than proof that every removed trip was garbage, because some genuine long journeys will have been thrown out along with the broken ones. We kept trips that lasted more than 0 and at most 120 minutes, had a recorded distance between 0 and 50 miles, had an average speed of at most 100 mph, and started and ended inside a rough box around the New York region that we put together from coordinates we found online.

One thing to be careful about: these rules remove trips based on their duration, distance and speed, so the set of trips we evaluate on changes as well. That means comparing the RMSE on the raw data with the RMSE on the cleaned data doesn’t cleanly measure how much the cleaning helped the model during training.

CHAPTER 03

Giving the model a distance instead of four coordinates

Baseline

Every comparison on this page is measured against the same baseline: Linear Regression on the original columns, meaning the pickup and dropoff coordinates and the passenger count, with no engineered features at all. We ran it at three stages of cleaning, so you can see how much the data alone changed it before any feature or stronger model was added. Keep in mind the caveat from Chapter 02, though: cleaning also changes which trips are evaluated, so the first two numbers aren’t directly comparable with the third.

Raw January 2016 data 57.2100 RMSE in minutes · MAE 10.2018
Partially cleaned data 52.7959 RMSE in minutes · MAE 9.8636
Final cleaned data 8.9366 RMSE in minutes · MAE 6.4234

A linear model sees four raw numbers, the latitude and longitude of the pickup and of the dropoff, and it has no way of turning them into a distance by itself, because distance on a sphere isn’t a weighted sum of coordinates. The Haversine formula does that conversion for us. The information was always in the data, and this feature simply hands it to the model in a form it can use.

Haversine distance, vectorised · original notebook 
def haversine_distance(lat1, lon1, lat2, lon2):
    R = 3958.8  # Earth radius in miles

    lat1 = np.radians(lat1)
    lon1 = np.radians(lon1)
    lat2 = np.radians(lat2)
    lon2 = np.radians(lon2)

    dlat = lat2 - lat1
    dlon = lon2 - lon1

    a = (
        np.sin(dlat / 2)**2
        + np.cos(lat1) * np.cos(lat2) * np.sin(dlon / 2)**2
    )

    c = 2 * np.arcsin(np.sqrt(a))

    return R * c

cleaned_data["haversine_distance"] = haversine_distance(
    cleaned_data["pickup_latitude"],
    cleaned_data["pickup_longitude"],
    cleaned_data["dropoff_latitude"],
    cleaned_data["dropoff_longitude"]
)

What one engineered feature did for the same model

On the final cleaned sample, adding Haversine distance took Linear Regression from an RMSE of 8.9366 minutes down to 6.4735 minutes.

Does the time of the trip add anything?

Next we added the day of the week and the pickup hour, both one-hot encoded, because rush hour on a Monday is obviously not the same as 3 a.m. on a Sunday. Linear Regression improved again, although by much less than it did when we gave it distance.

An early warning about letting a tree grow as deep as it likes

Early on, before the final cleaning, we trained a decision tree with no depth limit at all. It fit the training data almost perfectly, with an RMSE of 4.8801, and then fell apart on the test set with an RMSE of 138.5187. That is a textbook case of overfitting. It isn’t a fair comparison with the final scores, though, because that tree was trained on the early, half-cleaned data.

Next to it we’ve put the boosting model from the final run, which scored 4.6653 on its own training data and 4.8957 on the test set. The question to ask of any model is how much worse it gets on data it hasn’t seen, and these two are about as different as it gets.

CHAPTER 05

What we can and can’t conclude from this

On the cleaned NYC sample, giving Linear Regression a meaningful geographic feature improved it a lot, and the weekday and hour features added smaller gains on top of that. The tree and the boosting model did better still with the final features, so the choice of model clearly mattered too.

Our takeaway from this case study: the way you represent your data can be one of the biggest sources of improvement you have, but it doesn’t make choosing a good model irrelevant.

There are real limits to this. We used a random train/test split instead of the time-based split we had planned, our duration and speed limits throw away some trips that were probably genuine, and the hour features still need a rerun after the bug fix. So please treat this as an exploration of one month in one city, and not as a rule for every tabular problem.

The starting point for all of this was the NeurIPS 2024 paper on data-centric evaluation of tabular models . NYC Taxi was our first test of that idea, and the other two case studies check whether its lessons carry over to different problems.
